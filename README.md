# rust-template

[中文文档](./README.zh-CN.md)

A one-command Rust project template. Distilled from [docs/engspec.md](./docs/engspec.md) — an engineering-spec study of Zed, rust-analyzer, DeepSeek Harness, LLVM, uv and other reference repositories — with every component of the Rust development and release pipeline pre-configured, so you only ever think about your core code.

## Quick start

Prerequisite: [Nix](https://nixos.org/download/) with flakes enabled (direnv optional but recommended).

```bash
mkdir my-cli && cd my-cli
nix run github:duskgrow/rust-template -- my-cli your-github-name   # copy + rename + strip + git init + stage + git hooks — one command
```

Equivalent two-step path: `nix flake init -t github:duskgrow/rust-template` (copy only, no git history), then `nix develop -c just init my-cli your-github-name`.

You end up with a project that looks hand-built from an empty repository: zero template residue (this README, the init script, the spec report, and the smoke-test CI job are all removed) and an empty git history — the whole tree is staged and the first commit is yours.

No Nix CLI? Mark this repo as a Template repository (Settings → General → Template repository) and click "Use this template" — a one-shot workflow initializes the new repository automatically (the repository name doubles as the project name, so keep it kebab-case; the workflow then deletes itself, and its GITHUB_TOKEN push does not trigger CI — your first push does). Equivalent local path: clone, then run `nix develop -c just init <name> <owner>`.

## The release flow (zero maintenance once set up)

1. Commit with Conventional Commits (`feat:` / `fix:` / `!` are version intent);
2. release-plz keeps a Release PR updated: version numbers, CHANGELOG, cargo-semver-checks verdict;
3. You click merge → it pushes tag `vX.Y.Z`, publishes to crates.io (OIDC, no long-lived token), and cargo-dist builds four platform targets and creates a GitHub Release with checksums and attestation.

One-time setup (~5 minutes) for a fresh repo: see [CONTRIBUTING.md — Releasing](./CONTRIBUTING.md#releasing).

## Layout

- `crates/<name>/` — your first crate (thin bin + testable lib skeleton, with an insta snapshot example)
- `justfile` — every automation entry point (`just --list`)
- `docs/decisions/` — the template's key decisions (ADRs); reset to a fresh starting point by `just init`
- `docs/engspec.md` — the engineering-spec report this template is distilled from (removed from your project by `just init`)

## Trimming

- Library-only project: delete `dist-workspace.toml` and `.github/workflows/release.yml`
- Not publishing to crates.io: set `publish = false` for the package in `release-plz.toml` (tags + GitHub Releases still work)
- No Windows support needed: drop the `test-windows` job in ci.yml and the msvc target in `dist-workspace.toml`
- Native Windows development: via WSL2 (see docs/decisions/0004)

## Contributing to the template itself

This repository follows the same rules it prescribes: `direnv allow && just ci` (entering the shell also arms the git hooks).

Every change here has **two identities** and must be thought through twice:

1. **As this repo** — `just ci` must stay green in the template itself (the placeholder crate `__project_name__` is a valid crate name, so the template is a real, buildable workspace).
2. **As every future generated project** — whatever init does not strip ships downstream: a new devShell tool, a workflow job, a rule in AGENTS.md. For each change, ask which identity it belongs to. Template-only content lives behind `# >>> template-only` / `# <<< template-only` fences (`// …` in Rust sources; stripped by the xtask `init` module) or in files init replaces/removes (this README, `docs/engspec.md`, `docs/decisions/`, the init module itself). Guidance for template maintainers therefore belongs in this README — never in CONTRIBUTING.md, which ships to generated projects.

The `smoke-init` CI job is the second identity's gate: it runs the full `just init` → `just ci` → `just dist-check` flow in a temporary directory, so a missed placeholder or a broken generated project fails the template's own CI. The bootstrap mechanism's rationale lives in `docs/decisions/0001`.
